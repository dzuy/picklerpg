# Full Game Analysis

This feature belongs to the shared [Premium access concept](PREMIUM.md). Billing is not implemented; the feature-specific entitlement below is an interim access mechanism.

Solo and Friends endscreens and Profile → Game history open the same Full Game Analysis modal. Game history lists completed solo and friends games newest first, including archived games, with the viewer’s final score first; synced solo copies are deduplicated and unfinished or ended-early games are excluded. Each entry exposes the shared Premium analysis action. Locked accounts see a feature preview; enabled accounts get an AI-written report with exact recorded-rally, shot and fireball counts, coverage labeling, a story headline and subheadline, and three coaching groups: The Good, Needed Improvements, and Next For You. Version 2 reports contain 2–3 focused points per group, each with evidence, tactical explanation, and a concrete coach’s cue. Next For You includes rematch priorities and a suggested real-court practice drill. Color-blocked sections, bullets, and shot-mix bars make the report easier to scan. Chart counts are computed directly from the recordings, not generated by AI; they describe shot selection, not success rate. While the request runs, an animated spinner and stage-specific messages cover access checks, recording sync, and AI generation. Reduced-motion preferences use a static indicator. The report replaces the loading state when the request succeeds; there is no simulated percentage or artificial delay. Closing the dialog returns focus to its endscreen or history entry. Failed requests offer retry; missing recordings never produce a fabricated report.

## Enable

- Deploy the gameplay-recording migration and server/client recording flow first (see GAMEPLAY-RECORDING.md).
- Configure server-only `OPENAI_API_KEY`. Optional `GAME_ANALYSIS_MODEL` overrides `OPENAI_MODEL`; otherwise the existing project default `gpt-5.6-luna` is used.
- Grant access through trusted Supabase **app metadata**: `full_game_analysis: true`. Never put this flag in user-editable metadata. No entitlement is granted by this code, and no billing, pricing, checkout, or subscription workflow is implied. Cosmetic pack ownership does not grant analysis access.
- The analysis endpoint shares the existing authenticated multiplayer API configuration, including `MULTIPLAYER_ENABLED=true` and the server Supabase credentials.

`GET /api/multiplayer/game-analysis/access` checks access without generating a report. `POST /api/multiplayer/game-analysis` accepts only `{gameId, mode:'solo'|'friends'}`. It verifies ownership/participation and completed status, then reads stored telemetry on the server. Solo client-supplied reports are never accepted in this request. Solo recorded gameplay itself remains client-reported.

Apply `supabase/migrations/202609280002_game_analyses.sql` before deploying this version. Generated reports, their coverage, and exact shot-mix counts are stored in `game_analyses`, keyed by requesting account, mode, and game ID, with the model and generation timestamp. The report is saved before it is returned. Later requests reuse that exact report, including after server restarts, model changes, or new telemetry; there is no automatic regeneration. Friends participants have separate reports because the analysis is written from each viewer’s perspective. Older reports held only in server memory cannot be recovered after that process exits.

An account can request six analyses per minute. At most four generations are active per process. Identical in-flight requests share work within a process; a database claim also prevents concurrent generation across processes. Interrupted claims expire after two minutes, while failed attempts release their own claim for retry. Completed reports cannot be reclaimed. Entitlement and game ownership are checked before reading a saved report. Saved reports remain available when the AI provider is unconfigured. Database tables and claim functions are accessible only to the service role, never directly to browser clients.

## Report contract

Headline, summary, story, featured rally, signature moves, opponent responses, rematch tip. Aim for 300–450 words: specific, warm, punchy, and useful after a loss as well as a win. Inputs contain exact aggregates, rules, ratings and selected real rally sequences, not names or account identifiers. The longest rally, final rally and most counter-heavy rally are candidates; sequences are limited to 40 shots and labeled when truncated. A highlight must not be described as a turning point without evidence. Player labels are relative to the viewer, including the away side in Friends.

The application calculates counts and coverage, not the model. Partial records are labeled independently of AI text. The model receives an instruction to avoid claims about unrecorded gameplay. Structured results are length-checked and rendered as plain text, never HTML. Provider failures/refusals yield retryable errors. Runtime statistics do not constitute evidence that the generated interpretation is correct; live wording still needs playtest review.

The Responses request uses structured JSON output and `store:false`, following [official Structured Outputs guidance](https://developers.openai.com/api/docs/guides/structured-outputs). Game facts are sent to the configured OpenAI model only when an enabled player clicks the button. No real provider calls are made by unit tests.

`tests/browser/full-game-analysis.html` is a design preview. Its example report is explicitly labeled, and is not a real generated analysis. Remove or exclude test preview pages from any production static distribution (the Vite production entry build does not publish this HTML).

## Format compatibility

New generations use structured report format version 2. Existing saved reports retain their original wording and are displayed within the coaching groups without a model call. They do not gain invented advice or chart data. No database migration is required for the new report shape; it lives in the existing JSON analysis field. The generation prompt distinguishes recorded game evidence from tactical hypotheses and suggested drills, and does not infer the human’s physical technique or real-world skill from simulation telemetry.
